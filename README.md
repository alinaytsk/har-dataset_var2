# har-dataset — RealWorld (HAR) для трекера активності на STM32

Підготовка датасету **RealWorld (HAR) 2016** до навчання моделі розпізнавання
активності, яка працюватиме локально на мікроконтролері. Трекер носиться на
**плечі (вище ліктя)**, тому з датасету береться тільки позиція `upperarm`.

На виході — `data/processed/{train,val,test}.npz` з вікнами **208 × 6** при
**104 Гц**, у фізичних одиницях (**g** і **°/с**), розділені **за людьми**.

```
X [N, 208, 6] float32 — ax, ay, az, gx, gy, gz
y [N] int64           — 0 Lying, 1 Stationary, 2 Walking, 3 Running, 4 Stairs
y_raw [N] int64       — оригінальний клас RealWorld
subject [N] int64     — номер учасника
```

| Беремо | Відкидаємо | Чому |
|---|---|---|

## 3. Обробка

Порядок кроків і всі числа — у [`config.yaml`](config.yaml); скрипти власних
значень не містять.

1. **Одиниці.** RealWorld пише дані Android-сенсорів: акселерометр у **м/с²**,
   гіроскоп у **рад/с** (перевірено на даних: у спокої `|acc| ≈ 10.1 м/с²`).
   Переводимо: `acc / 9.80665 → g`, `gyro × 180/π → °/с`.
   Контроль після обробки: `|acc|` для Lying 0.976–0.985 g, для Stationary
   1.031–1.038 g — тобто ≈ 1 g, як і має бути.
2. **Синхронізація.** acc і gyro пишуться незалежно й починаються в різні
   моменти, тому беремо **тільки спільний часовий інтервал** і інтерполюємо
   обидва сенсори на одну часову сітку.
3. **Обрізання країв:** по **3 с** з початку і кінця кожного запису — там
   учасник бере/кладе телефон.
4. **Розриви.** У сирих мітках часу трапляються провали (типово 12 розривів
   по ~1.5 с на 10-хвилинний запис). Розрив **> 0.5 с** не інтерполюється:
   запис ріжеться на окремі неперервні сегменти. Вікно **ніколи** не перетинає
   розрив, межу запису, активності чи учасника.
5. **Кілька записів однієї активності.** В учасників s4, s7, s14 сходи записані
   у 3 частини (вкладені zip `_1`, `_2`, `_3`) — кожна частина обробляється як
   окремий запис.
6. **Ресемплінг 50 → 104 Гц.** Спершу інтерполяція на рівномірну сітку 50 Гц
   (прибирає джитер міток часу), далі `scipy.signal.resample_poly(up=52, down=25)`
   — 50 × 52/25 = 104 Гц, з вбудованим інтерполяційним FIR-фільтром.
   **Важливо:** сирі дані записані на ~50 Гц, тому підвищення до 104 Гц **не додає
   нової частотної інформації** — вище 25 Гц (Найквіст джерела) реального сигналу
   немає. Це узгодження формату з частотою плати, а не збільшення деталізації.
   Окремо: запис `s14/climbingdown` частина 1 писався гіроскопом із кроком 2 мс
   (~101 Гц); перед зниженням до 50 Гц до нього застосовано ФНЧ Баттерворта
   20 Гц, інакше був би аліасинг. Таких записів один зі 117.
7. **Канали** в порядку `ax, ay, az, gx, gy, gz`.
8. **Вікна:** 208 відліків (2.0 с), крок 104 (перекриття 50 %). Неповне останнє
   вікно відкидається.
9. **Нормалізація у файлах відсутня** — дані лишаються у фізичних одиницях.
   `mean`/`std` по 6 каналах порахувані **тільки на train** і лежать окремо в
   `data/processed/norm_stats.json`.

## 5. Розділення за людьми і кількість вікон

Жоден учасник не потрапляє у дві вибірки — інакше модель вчила б людину, а не
активність. Скрипт падає з помилкою, якщо списки в `config.yaml` перетинаються.

| Вибірка | Учасники | Вікон | Годин (без перекриття) |
|---|---|---|---|
| train | 1, 2, 3, 4, 5, 7, 8, 9, 11, 13 | 42 052 | 11.68 |
| val | 6, 10 | 7 818 | 2.17 |
| test | 12, 14, 15 | 11 841 | 3.29 |
| **разом** | 15 | **61 711** | **17.14** |

Кількість вікон по класах:

| Клас | train | val | test |
|---|---|---|---|
| 0 Lying | 6 002 (14.3 %) | 1 198 (15.3 %) | 1 785 (15.1 %) |
| 1 Stationary | 11 885 (28.3 %) | 2 436 (31.2 %) | 3 516 (29.7 %) |
| 2 Walking | 6 071 (14.4 %) | 1 182 (15.1 %) | 1 834 (15.5 %) |
| 3 Running | 7 048 (16.8 %) | 1 227 (15.7 %) | 1 786 (15.1 %) |
| 4 Stairs | 11 046 (26.3 %) | 1 775 (22.7 %) | 2 920 (24.7 %) |

**Про дисбаланс.** Класи нерівні: `Stationary` (sitting + standing) і `Stairs`
(climbingup + climbingdown) зібрані з двох активностей кожен, тому їх приблизно
вдвічі більше. Дисбаланс **навмисно не вирівнюється** — ні обрізанням, ні
дублюванням вікон: це спотворило б реальний розподіл і зменшило обсяг даних.
Компенсувати слід **при навчанні**, вагами класів, наприклад
`class_weight='balanced'` або `weight = N / (K × n_клас)` у функції втрат.
Пропорції однакові в усіх трьох вибірках, тому val/test лишаються чесними.

## 6. Формат вихідних файлів

`data/processed/train.npz`, `val.npz`, `test.npz`:

| Масив | Форма | Тип | Опис |
|---|---|---|---|
| `X` | (N, 208, 6) | float32 | вікна, НЕ нормалізовані: acc у g, gyro у °/с |
| `y` | (N,) | int64 | цільовий клас 0…4 |
| `y_raw` | (N,) | int64 | оригінальний клас RealWorld 0…7 |
| `subject` | (N,) | int64 | номер учасника |
| `channels` | (6,) | str | `ax, ay, az, gx, gy, gz` |
| `class_names`, `raw_class_names` | | str | назви класів |
| `fs`, `window_samples`, `stride_samples`, `units` | | | метадані (104.0, 208, 104, `g`/`dps`) |

> **Розміри:** `train.npz` — 189 МБ, `val.npz` — 18 МБ, `test.npz` — 27 МБ.
> `train.npz` перевищує ліміт GitHub на окремий файл (100 МБ), тому для нього
> потрібен Git LFS — або не комітити його взагалі: він відтворюється за ~2 хв
> командою `python scripts/run_all.py --skip-download`, якщо є `data/raw/`.

* `data/processed/norm_stats.json` — `mean` і `std` по 6 каналах **з train**.
* `data/processed/label_map.json` — мапінг `y`, `y_raw`, позиція, канали, одиниці.

### Приклад завантаження

```python
import json
import numpy as np

train = np.load("data/processed/train.npz")
X, y, subject = train["X"], train["y"], train["subject"]   # (N,208,6), (N,), (N,)
classes = [str(c) for c in train["class_names"]]           # ['Lying', ...]

# Нормалізація статистиками train (їх же зашивати у прошивку):
stats = json.load(open("data/processed/norm_stats.json", encoding="utf-8"))
mean = np.array(stats["mean"], dtype="float32")
std = np.array(stats["std"], dtype="float32")
Xn = (X - mean) / std

# Тільки акселерометр (3 канали) — якщо модель навчається без гіроскопа:
X_acc = X[..., :3]            # (N, 208, 3): ax, ay, az
X_gyr = X[..., 3:]            # (N, 208, 3): gx, gy, gz
```

## 7. Вимоги до прошивки

Щоб дані з плати збігалися з тими, на яких навчена модель:

| Параметр | Значення |
|---|---|
| ODR | **104 Гц** для акселерометра і гіроскопа (рівно, інакше вікно 208 відліків ≠ 2.0 с) |
| Вікно | буфер **208 × 6**, крок 104 відліки (перекриття 50 %) |
| Канали і порядок | `ax, ay, az, gx, gy, gz` — спершу акселерометр, потім гіроскоп |
| Одиниці | акселерометр у **g**, гіроскоп у **°/с** (не м/с² і не рад/с!) |
| Позиція | на плечі, вище ліктя |
| Нормалізація | `(x − mean) / std` зі `norm_stats.json`, ті самі 6 пар чисел |
| Гравітація | **не віднімається** — постійна складова acc розрізняє Lying і Stationary |
| **ФНЧ перед інференсом** | **25 Гц обов'язково** — див. нижче |
| Втрачені відліки | провал до `max_gap_seconds` добивати інтерполяцією, більший — починати вікно заново |

**Чому ФНЧ 25 Гц обов'язковий.** Джерело датасету записане на 50 Гц, тому реального
сигналу вище 25 Гц у навчальних даних немає — там нуль. Датчик на платі, працюючи на
104 Гц, шумить у цю смугу по-справжньому. Без фільтра модель отримує на вході те,
чого ніколи не бачила під час навчання. Вбудовані фільтри ISM330DHCX не підходять:
LPF2 акселерометра дає максимум ODR/10 = 10.4 Гц (зрізало б корисний сигнал), а LPF1
гіроскопа задається «силою», а не частотою.

**Щоб прошивка і датасет не розходилися**, константи для неї генеруються:

```bash
python scripts/export_firmware_constants.py
```

Скрипт пише `Core/Inc/har_model_config.h` (шлях — `firmware.core_dir` у `config.yaml`)
з частотою, розміром вікна, порядком каналів, одиницями, назвами класів, `mean`/`std`
з `norm_stats.json` і коефіцієнтами ФНЧ у вигляді SOS. Редагувати заголовок руками
не можна — міняти треба `config.yaml` і перегенерувати.

Реалізація на боці плати — `Core/Src/har_preproc.c` (ФНЧ, накопичення вікна,
нормалізація). Вона звіряється з еталоном на scipy прямо з цього репозиторію:

```bash
python tests/test_har_preproc.py
```

Тест збирає прошивковий код звичайним `gcc` (ARM-тулчейн не потрібен) і перевіряє,
що фільтр посемпльно збігається зі `scipy.signal.sosfilt`, що смуга вище зрізу
справді давиться, що вікна виходять з правильним кроком і що нормалізація — це
рівно `(x - mean) / std`.

Якщо модель навчатиметься лише на акселерометрі (`X[..., :3]`), гіроскоп у
прошивці можна не читати, але решта параметрів лишається незмінною.

## 8. Відтворення

```bash
pip install -r requirements.txt

# усе одразу: завантаження -> обробка -> вікна -> перевірки
python scripts/run_all.py

# або покроково
python scripts/download.py        # ~0.75 ГБ архівів -> data/raw/
python scripts/preprocess.py      # сегменти 104 Гц -> data/interim/
python scripts/make_windows.py    # вікна і вибірки -> data/processed/
python scripts/checks.py          # перевірки і графіки -> reports/

# константи для прошивки (після будь-якої зміни параметрів)
python scripts/export_firmware_constants.py
python tests/test_har_preproc.py  # звірка ФНЧ прошивки зі scipy

# швидка перевірка пайплайна на двох учасниках
python scripts/run_all.py --subjects 1,2
```

Корисні ключі: `download.py --check-only` (перевірити доступність і розмір),
`download.py --all-positions` (розпакувати всі позиції на тілі),
`run_all.py --skip-download`, `checks.py --verify-rerun` (перезапустити нарізку
і звірити хеші файлів).

Прогін відтворюваний: `seed: 42` у `config.yaml`, а `.npz` пишуться з фіксованими
мітками часу всередині zip, тому **повторний запуск дає байт-у-байт ідентичні
файли** (перевірено, див. `reports/checks.md`).

## 9. Перевірки

`python scripts/checks.py` формує `reports/checks.md`, `reports/checks.json` і
графіки. Станом на останній прогін пройдено все:

| Перевірка | Результат |
|---|---|
| форми і типи масивів відповідають специфікації | OK |
| немає NaN/inf | OK (0 у всіх вибірках) |
| учасники не перетинаються між вибірками | OK |
| у кожного учасника є `upperarm` для кожної активності | OK (117 записів) |
| у val і test присутні всі 5 класів | OK |
| \|acc\| для Lying і Stationary ≈ 1 g | OK (0.976 … 1.038 g) |
| діапазони каналів фізично можливі | OK (acc ±2.4 g, gyro ±687 °/с) |
| повторний запуск дає ідентичні файли | OK |

Графіки в `reports/`: `class_distribution.png` (розподіл класів по вибірках),
`subject_class_matrix.png` (вікна в розрізі учасник × клас),
`windows_0_Lying.png` … `windows_4_Stairs.png` (приклади вікон, 6 каналів).
